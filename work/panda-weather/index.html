Case study

Panda Weather

A responsive weather dashboard. Search a city, compare up to five widgets, and keep favorites in the browser.

Role
Solo developer
Period
2026
Project type
Weather dashboard
  • Vue 3
  • TypeScript
  • Pinia
  • Chart.js
  • Cloudflare Workers

Overview

A weather dashboard for a Panda Team assessment.

The repository goals are city search with autocomplete, current conditions, a Chart.js temperature forecast, several independent widgets, favorite cities, English and Ukrainian, and a layout that works from a phone up to a desktop width.

The shipped app covers that list. It has no accounts, no cloud sync of favorites, and no hourly forecast product. OpenWeatherMap’s five-day feed arrives in three-hour steps, and the charts use those timestamps.

My role

The Vue app, the charts, and the Worker.

I built the Vue 3 interface, the Pinia stores, the Chart.js charts, and the Cloudflare Worker that proxies OpenWeatherMap. GitHub Actions publishes the production build from main to GitHub Pages.

Architecture

Vue and Pinia in front of one Worker.

City search

One query, one widget.

  1. 01

    Autocomplete waits 300ms, ignores a trimmed query shorter than 2 characters, and cancels the previous lookup.

  2. 02

    Choosing a suggestion sets the location on that widget only. Another widget’s search does not change it.

  3. 03

    Current weather and the forecast load together. A late response is kept only when it still belongs to that widget.

  4. 04

    The dashboard opens with one widget and stops at five. Removal asks for confirmation. The last widget cannot be removed.

The first widget can start from an approximate IP location. If that lookup is missing or fails, the fallback city is London. The browser does not ask for GPS.

Forecast

Current conditions, then two chart ranges.

Each card shows the city, temperature in Celsius, a condition icon, and feels-like, humidity, wind, and pressure when the response includes them. Wind is meters per second. Empty optional fields are hidden rather than filled in.

24 Hours draws the three-hour entries from the current time through the next 24 hours, in the city’s offset. 5 Days keeps the first five local dates and charts the average of the temperatures that exist on each date. Missing slots are not invented. Chart.js runs on the canvas directly, one instance per widget, and that instance is destroyed when the widget goes away.

Favorites

Saved cities, and a second language.

Favorites is its own tab. Those widgets show weather without a city search. A city is stored by latitude and longitude, so a duplicate name does not create a second entry. The list stops at five cities. A further add explains that one favorite has to be removed first. Only the city list is written to localStorage. Forecast payloads stay in memory.

The interface is English and Ukrainian. Weather descriptions are requested with lang=en or lang=uk. Day and Night are a saved theme, and Day is the default. The theme is not taken from the clock or from a widget’s 24 Hours / 5 Days switch. A missing or unreadable setting falls back to English and Day.

API proxy

The key stays on the Worker.

The browser calls only this project’s Cloudflare Worker: GET /geocoding, GET /weather, and GET /forecast. The Worker validates the query, calls OpenWeatherMap with units=metric, and adds appid from the OPENWEATHER_API_KEY secret. That secret is not a Vite variable, not part of the frontend bundle, and not a GitHub Actions variable.

The production build rejects an http API base URL and rejects an openweathermap.org host. The deployed Worker allows the portfolio origins plus local localhost and 127.0.0.1. CORS is a browser check, not a login. The app has no user authentication. Upstream error bodies and any payload that contains the key are not returned to the browser.

Interface

Responsive layout, and a few hard limits.

The widget grid is three columns on a wide screen, two columns from 1024px, and one column from 640px. The specification’s minimum width is 360px, and the desktop container reference is 1200px. City suggestions, the Weather and Favorites tabs, and the confirmation dialogs are keyboard accessible. Each widget has its own loading and error state, so one failed request leaves the others in place.

Raw OpenWeatherMap payloads stay inside the service layer. The UI reads normalized TypeScript models. There is no vue-chartjs wrapper, no CSS framework, and no Vue Router. Provider rate limiting is not implemented in the Worker. A provider HTTP 429 is shown as a rate-limit error when it happens.
