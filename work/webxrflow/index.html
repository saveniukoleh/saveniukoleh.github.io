Case study

WebXRFlow

An early-stage browser CMS for WebXR scenes. Accounts and project records are in place. The 3D editor and immersive sessions are not in this repository.

Role
Solo developer
Period
2025–2026
Project type
WebXR CMS Prototype
  • Vue 3
  • TypeScript
  • Pinia
  • Firebase
  • GitHub Pages

Overview

A project dashboard in front of a future editor.

The plan is a signed-in place to create a project, edit a 3D scene, save it as JSON, and open it in the browser, in AR, or in VR. What runs is the account and project slice: email and Google sign-in, a dashboard that creates, lists, and deletes project documents, and routes reserved for the editor, gallery, and viewer.

The marketing home describes the product direction for people building AR and VR scenes on the web. Planning notes describe a one-developer MVP. The running build is an early-stage browser CMS with authentication, project management, and Firebase integration—not a live creator platform or finished visual editor.

My role

Architecture, the Vue app, and Firebase.

I set the application structure, built the screens, and connected Firebase Authentication and Firestore. Every commit on main is authored by me. The October 2026 commits publish the demo on GitHub Pages.

Core implementation

Sign in, then a project document.

  1. 01

    Register or sign in with email and password, or with a Google popup. The first sign-in writes a profile at users/{uid}.

  2. 02

    The dashboard lists that person’s projects, creates one from a dialog, and deletes it after confirmation.

  3. 03

    A new document stores a title, a description, isPublished: false, and sceneData with version 1.0 and an empty objects array.

  4. 04

    Editor, gallery, and viewer routes open from there. They do not load the document, and they do not render a scene.

Architecture

Vue and Pinia in front of Firebase.

Development challenges

Subpath deploy, the project query, and the auth guard.

  1. 01

    The demo lives at /webxrflow/ on an existing site, while local dev stays at /. The Vite base is /webxrflow/ only when GITHUB_PAGES is set, and the router uses that base. GitHub Pages does not rewrite unknown paths, so the workflow copies index.html to 404.html. Deep links return HTTP 404 with the app shell, and Vue can still start.

  2. 02

    A user’s project list filters on userId and sorts by updatedAt in the browser. That avoids a composite Firestore index. The published-projects query still uses orderBy, and no screen calls it.

  3. 03

    Firebase restores the user asynchronously. The route guard treats an empty user as signed out and does not wait, so a refresh of the dashboard can land on login. That gap is still open.
